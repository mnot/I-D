Binary Structured HTTP Field Values

Abstract

This specification defines a binary serialisation of Structured Field Values for HTTP, along with a negotiation mechanism for its use in HTTP/2.¶

1. Introduction

Structured Field Values for HTTP [STRUCTURED-FIELDS] offers a set of data types for use by HTTP fields, along with a serialisation of them in a familiar textual syntax.¶

Section 2 defines an alternative, binary serialisation of those structures, and Section 3 defines a mechanism for using that serialisation in HTTP/2.¶

The primary goal of this specification is to reduce parsing overhead and associated costs, as compared to the textual representation of Structured Fields. The saving is expected to be largest for Byte Sequences (such as signatures and digests), which need no base64 decoding, and for Strings that need unescaping; it is expected to be small for short Tokens and Dictionaries. A secondary goal is a more compact wire format in common situations. An additional goal is to enable future work on more granular field compression mechanisms.¶

1.1. Notational Conventions

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all capitals, as shown here.¶

This specification describes wire formats using the convention described in Section 1.3 of [QUIC].¶

Several types carry text as a String Literal, which is the String Literal Representation defined in Section 5.2 of [RFC7541]: an H flag, a Length encoded as an integer with a 7-bit prefix (Section 5.1 of [RFC7541]), and that many octets of data. If H is set, the data is Huffman-coded, as the sender chooses for each string. Every constraint that this specification places on such a string applies to its octets after any Huffman decoding. Other integers, written (i) in the diagrams, use the integer representation from Section 5.1 of [RFC7541] with an 8-bit prefix, so a value below 255 takes one octet. This is not the variable-length integer that Section 1.3 of [QUIC] denotes with the same notation. A recipient MUST treat an integer greater than 2^62 - 1 as malformed.¶

2. Binary Structured Types

This section defines a binary serialisation for Structured Field Values as defined in [STRUCTURED-FIELDS].¶

A Structured Field Value can be a singular Item (such as a String, an Integer, or a Boolean, possibly with parameters), or it can be a compound type, such as a Dictionary or List, whose members are composed of those Item types.¶

When a field value is serialised as a Binary Structured Field, each of these types is preceded by a header octet that indicates the relevant type, along with some type-specific flags. The type then determines how the value is serialised in the following octet(s).¶

Binary Structured Type {
  Type (5),
  Flags (3),
  [Payload (..)]
}
¶

Use of each flag may not be specified by all types. When this is the case, generators MUST send 0 for them, and recipients MUST ignore them. An extension that is negotiated with a larger value of SETTINGS_BINARY_STRUCTURED_FIELDS (Section 3.1) can give them meaning.¶

2.1. Recipient Validation

A recipient of a Binary Structured Field Value MUST check it against the constraints in this section, which carry over the restrictions that [STRUCTURED-FIELDS] places on the textual form. The sections for each type state the checks on its payload. Checks that apply to the value as a whole are:¶

  • Every Type is defined by this specification, or by an extension that the recipient supports (see Section 3.1).¶

  • No Member Count, Parameter Count or Length (including the Length of a String Literal) reaches past the end of the field value, and no octets remain after the top-level type and any Parameters that follow it.¶

  • Each type appears only where [STRUCTURED-FIELDS] allows that data type: the top-level type is a List, a Dictionary or an Item; the members of Lists and Dictionaries are Items or Inner Lists; the members of Inner Lists and the values of Parameters are Items.¶

  • The Parameters Flag is never set on the value of a Parameter (Section 2.6).¶

A value that fails any of these checks is malformed; see Section 3.3.¶

A recipient that skipped these checks could accept values that the textual form cannot express, and then be unable to serialise them for a peer that does not support this specification (see Section 3.1).¶

2.2. Literal Values

A Literal Value is a special type that carries the string value of a field; they are used to carry field values that are not structured using the data types defined in Section 3 of [STRUCTURED-FIELDS]. This might be because the field is not recognised as a Structured Field, or it might be because a field that is understood to be a Structured Field cannot be parsed successfully as one.¶

A literal value's payload is a String Literal holding the field value, so a Literal Value costs one octet more than the String Literal Representation it replaces in [RFC7541].¶

Literal Value {
  Type (5) = 0,
  Unused Flags (3) = 0,
  String Literal (..)
}
¶

A recipient MUST apply the field value validation in Section 8.2.1 of [HTTP2] to the string.¶

2.3. Lists

A List (Section 3.1 of [STRUCTURED-FIELDS]) uses its Flags to carry a Short Member Count as three bits.¶

If the Short Member Count is zero, the Member Count follows the header octet. Otherwise, the Short Member Count is the Member Count itself. This allows a List of up to seven members to be encoded without an extra octet for its length.¶

In either case, the count is the number of List members that follow. A List MUST have at least one member: as in Section 4.1 of [STRUCTURED-FIELDS], a field whose value would be an empty List is not sent. A recipient MUST treat a List with a Member Count of zero as malformed.¶

List {
  Type (5) = 1,
  Short Member Count (3),
  [ Member Count (i) ],
  Binary Structured Type (..) ...
}
¶

2.4. Dictionaries

A Dictionary (Section 3.2 of [STRUCTURED-FIELDS]) uses its Flags to indicate its number of members, in a fashion similar to Lists. A Dictionary MUST have at least one member, for the same reason.¶

Dictionary {
  Type (5) = 2,
  Short Member Count (3),
  [ Member Count (i) ],
  Dictionary Member (..) ...
}
¶

Each Dictionary member is represented by a String Literal holding the member-key, followed by the Binary Structured Type(s) representing the member-value.¶

Dictionary Member {
  Member Key (String Literal),
  Binary Structured Type (..),
}
¶

A Member Key is at least one octet long. Its first octet MUST be a lowercase letter (0x61 to 0x7A) or "*", and each following octet MUST be a lowercase letter, a digit, or one of "_", "-", "." and "*" (see Section 4.2.3.3 of [STRUCTURED-FIELDS]). If a Member Key occurs more than once in a Dictionary, the last value overwrites the earlier ones, and the key keeps the position of its first occurrence (see Section 4.2.2 of [STRUCTURED-FIELDS]).¶

2.5. Inner Lists

An Inner List (Section 3.1.1 of [STRUCTURED-FIELDS]) uses two of its Flags to carry a Short Member Count, in the same way as a List: if it is zero, the Member Count follows the header octet; otherwise, it is the Member Count itself. Unlike a List, an Inner List can be empty (Section 3.1.1 of [STRUCTURED-FIELDS]), which is sent with a Short Member Count of zero and a Member Count of zero. The members follow.¶

Inner List {
  Type (5) = 3,
  Parameters (1),
  Short Member Count (2),
  [ Member Count (i) ],
  Binary Structured Type (..) ...
  [Parameters (..)]
}
¶

The Parameters Flag indicates whether the value is followed by Parameters (see Section 2.6).¶

Parameters on the Inner List itself, if present, follow its last member (Section 2.6); they do not form part of the payload of the Inner List (and therefore are not counted in Member Count).¶

2.6. Parameters

Parameters (Section 3.1.2 of [STRUCTURED-FIELDS]) are not a Binary Structured Type of their own. An Item or Inner List whose Parameters Flag is set is followed by Parameters, in this form:¶

Parameters {
  Parameter Count (i),
  Parameter (..) ...
}
¶

A recipient MUST treat a Parameter Count of zero as malformed, because the textual form cannot express a set of Parameters with no members.¶

Each Parameter conveys a key and a value:¶

Parameter {
  Parameter Key (String Literal),
  Binary Structured Type (..)
}
¶

A parameter's fields are:¶

  • Parameter Key: A String Literal holding the parameter-key¶

  • Binary Structured Type: The parameter value¶

The Binary Structured Type in a Parameter is an Item; it MUST NOT be an Inner List, and its Parameters Flag MUST NOT be set.¶

A Parameter Key is validated in the same way as a Member Key (see Section 2.4). Duplicates are handled as for Member Keys (see Section 4.2.3.2 of [STRUCTURED-FIELDS]).¶

2.7. Integers

An Integer (Section 3.3.1 of [STRUCTURED-FIELDS]) has a payload consisting of a single integer. The Sign flag is set (1) if the value is negative, and clear (0) otherwise; a generator MUST NOT set it for zero, so that each value has one encoding.¶

Integer {
  Type (5) = 5,
  Parameters (1),
  Sign (1),
  Unused Flag (1) = 0,
  Payload (i)
}
¶

The Parameters Flag indicates whether the value is followed by Parameters (see Section 2.6).¶

A recipient MUST treat an Integer whose payload exceeds 999,999,999,999,999 (the range limit in Section 3.3.1 of [STRUCTURED-FIELDS]) as malformed, even though the integer representation can carry larger values.¶

2.8. Decimals

A Decimal (Section 3.3.2 of [STRUCTURED-FIELDS]) has a payload consisting of a single integer that carries a Scale and a Mantissa, as described below. The Sign flag is set (1) if the value is negative, and clear (0) otherwise; a generator MUST NOT set it for zero, so that each value has one encoding.¶

Decimal {
  Type (5) = 6,
  Parameters (1),
  Sign (1),
  Unused Flag (1) = 0,
  Payload (i)
}
¶

The Parameters Flag indicates whether the value is followed by Parameters (see Section 2.6).¶

The two low-order bits of the payload are the Scale, which is the number of digits after the decimal point (0 to 3). The remaining bits are the Mantissa, so the value is the Mantissa divided by 10 to the power of the Scale. For example, 4.5 has a Mantissa of 45 and a Scale of 1, so its payload is 181 (45 * 4 + 1); -0.25 has a Mantissa of 25, a Scale of 2, a payload of 102, and the Sign flag set. A Scale of 0 is a Decimal whose fractional part is zero; it is still a Decimal, not an Integer, and the textual form serialises it with a ".0".¶

Generators MUST use the smallest Scale that represents the value exactly, so that each value has one encoding. A recipient MUST treat a Decimal whose Mantissa is 10 to the power of (12 + Scale) or greater as malformed, because its integer component would have more than twelve digits (Section 3.3.2 of [STRUCTURED-FIELDS]).¶

2.9. Strings

A String (Section 3.3.3 of [STRUCTURED-FIELDS]) has a payload that is a String Literal.¶

String {
  Type (5) = 7,
  Parameters (1),
  Unused Flags (2) = 0,
  String Literal (..)
}
¶

The Parameters Flag indicates whether the value is followed by Parameters (see Section 2.6).¶

Each octet of the string MUST be in the range 0x20 to 0x7E (inclusive), as in Section 3.3.3 of [STRUCTURED-FIELDS]. A recipient MUST treat a String that contains any other octet as malformed.¶

2.10. Tokens

A Token (Section 3.3.4 of [STRUCTURED-FIELDS]) has a payload that is a String Literal.¶

Token {
  Type (5) = 8,
  Parameters (1),
  Unused Flags (2) = 0,
  String Literal (..)
}
¶

The Parameters Flag indicates whether the value is followed by Parameters (see Section 2.6).¶

The first octet of the string MUST be a letter (0x41 to 0x5A or 0x61 to 0x7A) or "*", and each following octet MUST be a "tchar" (Section 5.6.2 of [HTTP]), ":" or "/" (see Section 3.3.4 of [STRUCTURED-FIELDS]). A recipient MUST treat a Token that is empty, or that contains any other octet, as malformed.¶

2.11. Byte Sequences

A Byte Sequence (Section 3.3.5 of [STRUCTURED-FIELDS]) has a payload consisting of an integer Length field, followed by that many octets of payload.¶

Byte Sequence {
  Type (5) = 9,
  Parameters (1),
  Unused Flags (2) = 0,
  Length (i),
  Payload (..)
}
¶

The Parameters Flag indicates whether the value is followed by Parameters (see Section 2.6).¶

The payload is Length octets long, containing the raw octets of the byte sequence.¶

2.12. Booleans

A Boolean (Section 3.3.6 of [STRUCTURED-FIELDS]) uses the Payload flag to indicate its value; if Payload is 0, the value is False; if Payload is 1, the value is True.¶

The Boolean data type carries its payload in the Payload Flag:¶

Boolean {
  Type (5) = 10,
  Parameters (1),
  Payload (1),
  Unused Flag (1) = 0,
}
¶

The Parameters Flag indicates whether the value is followed by Parameters (see Section 2.6).¶

2.13. Dates

A Date (Section 3.3.7 of [STRUCTURED-FIELDS]) has a payload consisting of a single integer, conveying the number of seconds since 1970-01-01T00:00:00Z, excluding leap seconds. The Sign flag is set (1) if the value is negative, and clear (0) otherwise; a generator MUST NOT set it for zero, so that each value has one encoding.¶

Date {
  Type (5) = 11,
  Parameters (1),
  Sign (1),
  Unused Flag (1) = 0,
  Payload (i)
}
¶

The Parameters Flag indicates whether the value is followed by Parameters (see Section 2.6).¶

A recipient MUST treat a Date whose payload exceeds 999,999,999,999,999 as malformed, as for an Integer.¶

2.14. Display Strings

A Display String (Section 3.3.8 of [STRUCTURED-FIELDS]) has a payload that is a String Literal.¶

Display String {
  Type (5) = 12,
  Parameters (1),
  Unused Flags (2) = 0,
  String Literal (..)
}
¶

The Parameters Flag indicates whether the value is followed by Parameters (see Section 2.6).¶

Its string is UTF-8 encoded ([UTF8]). Unlike the textual form, it is not percent-encoded. A recipient MUST treat a string that is not valid UTF-8 as malformed.¶

3. Using Binary Structured Fields in HTTP/2

When both peers on a connection support this specification, they can negotiate to serialise fields that they know to be Structured Fields as binary data, rather than strings.¶

Peers advertise and discover this support using a HTTP/2 setting defined in Section 3.1, and convey Binary Structured Fields in streams whose HEADERS frame uses the flag defined in Section 3.2.¶

3.1. The SETTINGS_BINARY_STRUCTURED_FIELDS Setting

Advertising support for Binary Structured Fields is accomplished using a HTTP/2 setting, SETTINGS_BINARY_STRUCTURED_FIELDS (0xTODO).¶

Receiving SETTINGS_BINARY_STRUCTURED_FIELDS with a non-zero value from a peer indicates that:¶

  1. The peer supports all of the Binary Structured Types defined in Section 2.¶

  2. The peer will process the BINARY_STRUCTURED HEADERS flag as defined in Section 3.2.¶

  3. When passing the message to a downstream consumer (whether on the network or not) who does not support this extension or otherwise explicitly negotiate an equivalent mechanism, the peer will:¶

    1. Transform all fields defined as Mapped Fields in Section 3 of [RETROFIT] into their unmapped forms, removing the mapped fields.¶

    2. Serialize all fields into the appropriate form for that peer (e.g., the textual representation of Structured Fields data types defined in [STRUCTURED-FIELDS]).¶

The default value of SETTINGS_BINARY_STRUCTURED_FIELDS is 0, whereas a value of 1 indicates that this specification is supported with no further extensions. Future specifications might use values greater than one to indicate support for extensions.¶

3.2. The BINARY_STRUCTURED HEADERS Flag

When a peer has indicated that it supports this specification as per Section 3.1, a sender can send the BINARY_STRUCTURED flag (0xTODO) on the HEADERS frame.¶

This flag indicates that the HEADERS frame containing it and subsequent CONTINUATION frames on the same stream use the Binary Structured Types defined in Section 2 instead of the String Literal Representation defined in Section 5.2 of [RFC7541] to represent all field values. Field names are still serialised as String Literal Representations.¶

In such frames, every field value that is carried in a literal representation MUST be sent as a Binary Structured Field Value. Note that this includes Binary Literals (Section 2.2) for those field values that are not recognised as Structured Fields, as well as textual values that cannot be successfully parsed as Structured Fields. Implementations MAY also send a field value as a Binary Literal even when it is possible to represent it as a Structured Field (e.g., for efficiency purposes).¶

Binary Structured Field Values are stored in the HPACK [RFC7541] dynamic table, and their lengths are used for the purposes of maintaining dynamic table size (see [RFC7541], Section 4). As in Section 4.1 of [RFC7541], the length of a Binary Structured Field Value is calculated without any Huffman encoding applied to its String Literals.¶

Each entry in the dynamic table has a representation: Binary if its value was inserted by a frame with the BINARY_STRUCTURED flag, and Textual otherwise. Entries in the static table are Textual. A recipient MUST record the representation with each dynamic table entry.¶

The representation belongs to the entry, not to the frame that refers to it. An indexed field representation obtains the entry's value in the entry's representation, whether or not the referring frame has the flag. A Textual value obtained in a frame with the flag is the value of an ordinary HTTP/2 field; it is not a Binary Literal. A Binary value obtained in a frame without the flag is a Binary Structured Field Value, and is serialised as text when its textual form is needed (see Section 3.1). A literal representation that refers to an entry only for its name is unaffected, because names are always String Literal Representations.¶

Note that HEADERS frames with and without the BINARY_STRUCTURED flag MAY be mixed on the same connection, depending on the requirements of the sender.¶

3.3. Malformed Binary Structured Field Values

A Binary Structured Field Value that fails a check in Section 2.1 makes the message that contains it malformed (Section 8.1.1 of [HTTP2]). Section 4.2 of [STRUCTURED-FIELDS] allows a failed parse to either ignore the field or make the message malformed; this specification requires the latter. A sender that cannot produce a valid Structured Field can send a Binary Literal (Section 2.2) instead, so an invalid value indicates a faulty sender.¶

The recipient MUST NOT stop decoding the field block at the malformed value, because HPACK decoder state would then diverge from the sender's. It completes decoding, and then handles the malformed message as Section 8.1.1 of [HTTP2] requires: as a stream error of type PROTOCOL_ERROR, without forwarding it.¶

If a value is malformed in a way that prevents the recipient from determining where it ends, the field block cannot be decoded. That is a decoding error, and the recipient MUST treat it as a connection error of type COMPRESSION_ERROR (Section 4.3 of [HTTP2]). A String Literal that cannot be Huffman decoded is a decoding error (Section 5.2 of [RFC7541]), and is handled in the same way.¶

5. Security Considerations

As is so often the case, having alternative representations of data brings the potential for security weaknesses, when attackers exploit the differences between those representations and their handling.¶

One mitigation to this risk is the strictness of parsing for both non-binary and binary Structured Fields data types (Section 2.1), along with the "escape valve" of Binary Literals (Section 2.2). Therefore, implementation divergence from this strictness can have security impact.¶

Appendix A. Changes from Previous Drafts

This section is to be removed before publishing as an RFC.¶

A.1. Since draft-nottingham-binary-structured-headers-03

  • Moved the Structured Fields reference to RFC 9651, and added Date (type 11) and Display String (type 12).¶

  • Integers use the RFC 7541 prefix integer representation instead of QUIC's variable-length integer, leaving one integer encoding in the draft.¶

  • Added recipient validation for each type (Section 2.1).¶

  • Defined malformed Binary Structured Field Values, and how a recipient handles them (Section 3.3).¶

  • Made duplicate Dictionary and Parameter keys last-wins, as in the textual form.¶

  • Parameters are no longer a Binary Structured Type; they follow their Item or Inner List as a Parameter Count and the Parameters (Section 2.6). Type 4 is unassigned.¶

  • Decimals are a Mantissa and a Scale in a single integer, rather than a dividend and a divisor (Section 2.8).¶

  • Made the representation (binary or textual) a property of each table entry, so frames with and without the BINARY_STRUCTURED flag can refer to each other's entries, and static table values are textual (Section 3.2).¶

  • Strings, Tokens, Display Strings, Literal Values and keys are String Literals, so the sender can Huffman-code each one (Section 2).¶

  • Narrowed the stated motivation to the fields where binary parsing is expected to save the most (Section 1).¶

  • The Sign flag is set for negative values, so the common case has all flags clear, and zero is never signed.¶

  • Clarified that the Member Count of a List or Dictionary follows the header octet, and that neither is ever empty (the field is omitted, as in the textual form).¶

  • Inner Lists carry a Short Member Count in their flags, as Lists do, and the text no longer requires them to have members.¶

  • Stated that extensions negotiated through the setting can give meaning to unused flags.¶
